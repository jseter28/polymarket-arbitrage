⏺ Here's the startup story, plain and simple:

  The Big Picture

  Think of the bot like a price-watching robot that compares prediction markets
  on two websites — Polymarket and Kalshi — looking for moments when the same
  event is priced differently. When you run python run_with_dashboard.py, here's
   what happens, step by step.

  ---
  1. You press "go" (main() → main_async())

  - The script reads your flags (--live, --port, --config).
  - It loads config.yaml (or config.live.yaml) — that's the robot's rulebook:
  which markets to watch, how big to bet, when to stop.
  - It sets up logging so you can see what it's doing.
  - Default mode is dry-run (fake money). You have to explicitly say --live to
  use real money.

  2. The bot wakes up (bot.start())

  It prints a big banner showing the mode, then builds its body part-by-part:

  a) Polymarket client — opens a connection to Polymarket so it can read prices
  and (in live mode) send orders.

  b) Kalshi client — if cross-platform mode is on, it opens a read-only
  connection to Kalshi too. Kalshi doesn't need a login for prices.

  c) Portfolio — a little notebook that tracks "how much money do I have? what
  positions do I own?" In dry-run it starts with fake money from config.

  d) Risk Manager — the safety guard. It says "no" if a trade would break the
  rules (too big, too risky, kill switch on, etc.).

  e) Execution Engine — the hand that actually places orders. Every order goes
  through the Risk Manager first.

  f) Arb Engine — the brain. Looks at prices and asks "is there free money
  here?" (e.g., YES + NO costs less than $1).

  g) Data Feed — the eyes. It connects to Polymarket via WebSocket and streams
  live order books. Every time a price changes, it whispers "hey brain, look at
  this!"

  3. The cross-platform side wakes up (in the background)

  Meanwhile, in a second thread of activity:
  - Downloads up to 5,000 Kalshi markets.
  - Waits until at least 50 Polymarket markets have loaded.
  - Then it plays a matching game: which Polymarket question is the same as
  which Kalshi question? (Uses fuzzy text similarity.)
  - This matching is heavy, so it runs in a separate thread so the dashboard
  doesn't freeze.
  - Once matches are found, the CrossPlatformArbEngine starts polling both sites
   and looking for price gaps.

  4. The dashboard opens (_start_server())

  A FastAPI web server boots up at http://localhost:8888. It runs alongside the
  bot and shows you:
  - Current prices, opportunities, trades, PnL, match progress.

  5. The bot just... runs

  - Every price update → Arb Engine analyzes → if an opportunity is found → Risk
   Manager checks → Execution Engine places the order (or pretends to, in
  dry-run).
  - In dry-run, a separate task fakes order fills randomly so the dashboard
  looks alive.
  - Cross-platform opportunities are logged and shown but NOT auto-traded
  (Kalshi client is read-only — no trading code for it yet).

  6. You press Ctrl+C → bot.stop()

  Gracefully shuts everything down in reverse:
  cross-platform engine → dashboard → data feed → execution engine → Polymarket
  client → Kalshi client → web server. Then it prints a final PnL summary.

  ---
  TL;DR — config loads → clients connect → safety + brain + eyes get wired
  together → dashboard opens → bot watches prices forever → Ctrl+C cleans up.
  Two trading "brains" run side-by-side: one for single-market arb on
  Polymarket, one for cross-platform arb between Polymarket and Kalshi.

⏺ Here are the actual polling rates, by source:

  Polymarket (real mode, REST polling)

  - Order books: rotates through markets in chunks of 500. Within each chunk: 50
   ms between individual market fetches, 300 ms between sub-batches of 20, 2 s
  between chunks. So any single market's book is refreshed roughly every time
  its 500-market chunk comes back around — typically several seconds to tens of
  seconds depending on how many markets you're watching.
  - Order books (simulation mode): 15 random markets per cycle, 20 ms apart,
  then 500 ms pause. Much faster — designed for demos.
  - Positions (REST): every 5 s (position_refresh_interval=5.0 in
  core/data_feed.py:40).
  - WebSocket ping: every 30 s (keep-alive, not data).

  Kalshi (REST polling — no WebSocket)

  - Order books: batches of 100 tickers fetched in parallel, then 2 s sleep
  before the next batch (kalshi_client/api.py:399). So with ~500 matched tickers
   you cycle every ~10 s.
  - Market list bootstrap: one-time at startup, up to 5,000 markets.

  Cross-platform arb engine

  - Uses Kalshi's stream_orderbooks under the hood with the same defaults:
  batch=100, rotation_delay=2 s (core/cross_platform_arb.py:599-600). On each
  Kalshi book update it instantly checks the cached Polymarket book — no
  separate timer.

  Housekeeping loops

  - Portfolio snapshot: every 60 s (config.yaml:110).
  - Heartbeat / health log: every 30 s (config.yaml:113).
  - Dry-run fill simulator: every 2 s, fills open orders with probability from
  config.

  Rough mental model

  - Polymarket prices = "rolling sweep" (each market re-checked every
  few-to-tens of seconds depending on universe size).
  - Kalshi prices = "batch sweep" (~2 s per 100-ticker batch).
  - Positions = every 5 s. Snapshots = every minute.

  The WebSocket is wired up for Polymarket (ping 30 s), but the actual
  order-book data path you're running is REST polling on the rotation schedule
  above.

❯ can we make polymarket faster?                                                

  Read 1 file (ctrl+o to expand)

⏺ Yes — and there's a lot of headroom. The current Polymarket loop is sequential
   (one market at a time, two REST calls each), which is the bottleneck. Here
  are the levers, cheapest to most ambitious:

  The bottleneck right now

  stream_orderbook loops through markets one-by-one and does two awaited REST 
  calls per market (YES book, NO book) with a 50 ms sleep between each. For 500
  markets that's roughly 2–3 minutes per full cycle before you even see a price
  again. Kalshi is faster because it uses asyncio.gather to fire a whole batch
  in parallel.

  Options (ranked by payoff / effort)

  1. Parallelize within the batch — biggest easy win. Replace the inner
  sequential loop with asyncio.gather like Kalshi does. A batch of 20 markets
  goes from ~6 s to ~300 ms (limited by the slowest single response). Roughly
  20× faster per cycle. Risk: hitting CLOB rate limits — you'd want to tune
  markets_per_request_batch down if you start getting 429s.

  2. Use Polymarket's CLOB batch endpoint (POST /books). Polymarket's CLOB API
  accepts a list of token IDs in one request and returns all their books. You'd
  cut the number of HTTP calls by ~20x on top of #1. This is the real "go fast"
  move but requires changing _fetch_token_orderbook to a _fetch_books_batch and
  reshaping the loop.

  3. Narrow the universe. Right now it streams every cached market. If your real
   goal is cross-platform arb on matched pairs, only stream the ~N matched
  market_ids. Fewer markets in the rotation = each one gets revisited sooner.
  Easy code change; doesn't fight the API.

  4. Switch to WebSocket (real-time push). There's already a stub in
  _connect_websocket with a TODO: Implement actual WebSocket connection and 
  subscription. This would give you sub-second updates and eliminate the
  rotation entirely. Bigger engineering lift — need to handle
  subscribe/unsubscribe, reconnects, and the diff message format — but it's the
  "right" answer long-term.

  5. Drop the sleeps. request_delay=50ms, batch_delay=300ms, rotation_delay=2s
  are conservative. You can lower them, but only meaningful after #1; right now
  the awaited HTTP latency dwarfs the sleeps.

  My recommendation

  Do #3 + #1 first (narrow + parallelize) — they're a few lines each and
  probably get you a 10–50× speedup without changing the API surface. Then
  evaluate whether #2 or #4 is worth the bigger change.

  Want me to implement #3 + #1? I'd parallelize the inner batch with
  asyncio.gather and add a config flag like stream_only_matched_markets: bool to
   scope the universe.

⏺ Got the protocol. Here's the concrete plan to wire up the real-time feed.

  What Polymarket gives you

  - Endpoint: wss://ws-subscriptions-clob.polymarket.com/ws/market (already in
  config.yaml:7)
  - No auth for market data
  - Subscribe payload (one message, all tokens at once):
  {
    "assets_ids": ["<yes_token_id>", "<no_token_id>", ...],
    "type": "market",
    "custom_feature_enabled": true
  }
  - Important gotcha: assets_ids = token IDs (the yes_token_id / no_token_id you
   already cache), NOT market_id / condition_id. The current stub at
  polymarket_client/api.py:715 sends market which is why it wouldn't work.
  - Heartbeat: send the literal string PING every 10 s; server replies PONG.
  (The websockets library's built-in ping won't satisfy this — Polymarket wants
  a text frame.)
  - Events you'll receive:
    - book — full snapshot (on subscribe and occasionally)
    - price_change — delta updates (per-level)
    - last_trade_price, best_bid_ask, tick_size_change, new_market,
  market_resolved

  The steps

  1. Fix the subscribe message (polymarket_client/api.py:701)
  Replace the per-market loop with a single batched send using the schema above.
   Build the assets_ids list from your _markets_cache (yes_token_id,
  no_token_id). Keep a reverse map token_id → (market_id, TokenType) so you can
  route incoming messages back to the right market.

  2. Add a receive loop
  Spawn asyncio.create_task(self._ws_recv_loop()). Inside: async for raw in 
  self._ws_connection: msg = json.loads(raw) and dispatch on msg["event_type"].

  3. Maintain local book state
  - On book: replace your cached OrderBook for that token wholesale.
  - On price_change: apply the deltas (per-price-level adds/removes) to the
  cached book.
  - After every update, combine the YES + NO half-books into your existing
  OrderBook dataclass and call the same callback the polling path uses
  (on_update(market_id, market_state)).

  4. Add the PING task
  async def _ws_heartbeat(self):
      while True:
          await asyncio.sleep(10)
          await self._ws_connection.send("PING")
  Spawn alongside the recv loop.

  5. Reconnect logic
  Wrap recv + heartbeat in an outer while self._running: with try/except 
  (ConnectionClosed, OSError). On disconnect: small backoff (asyncio.sleep(1)),
  reconnect, re-send the subscribe message with the same assets_ids. The server
  doesn't remember subscriptions across connections.

  6. Wire it into DataFeed
  DataFeed currently consumes stream_orderbook() (REST). Either:
  - Add a new stream_orderbook_ws() and switch DataFeed.start() to use it when
  data_mode == "real" and a flag like use_websocket: true is set, OR
  - Make stream_orderbook itself prefer WS and fall back to REST polling on
  failure.

  I'd add a use_websocket flag in config so you can toggle and A/B against the
  polling path.

  7. Sanity-check the round trip
  Once running, log a counter of updates/sec per market. With 500 active markets
   you should see hundreds of price_change events per minute vs. the ~5/min the
  polling loop produces.

  Effort estimate

  - Steps 1–4: ~150 lines, half a day. This alone gets you real-time.
  - Step 5 (reconnect): ~50 lines, another hour. Worth doing before you trust it
   overnight.
  - Step 6 (integration): ~30 lines.
  - Step 7 (instrumentation): trivial.

  flag, leaving the REST polling path intact as a fallback?

     Plan: Real-time Polymarket WebSocket feed with REST fallback

     Context

     The bot currently reads Polymarket order books via REST polling
     (polymarket_client/api.py:582-674). Each market requires two sequential
     REST calls (YES + NO token books) with built-in sleeps; with ~thousands of
     cached markets the full rotation takes minutes per market. This is the
     dominant data-latency bottleneck and a blocker for any latency-sensitive
     arb strategy.

     Polymarket exposes a no-auth WebSocket market channel
     (wss://ws-subscriptions-clob.polymarket.com/ws/market) that pushes
     sub-second book snapshots and price_change deltas. A stub exists at
     polymarket_client/api.py:701-728 but is unused and uses the wrong wire
     format.

     This plan adds a working WebSocket data path behind a use_websocket config
     flag, defaulting on. On connect failure or repeated disconnects, the client
      transparently falls back to REST polling while a supervisor retries WS
     every 20s and hot-swaps back when it succeeds. Existing REST code is
     preserved unchanged as the fallback.

     Design decisions (confirmed)

     - Flag location: mode.use_websocket: bool, default true, in
     utils/config_loader.py ModeConfig and config.yaml.
     - Subscription scope: every market in _markets_cache with valid
     yes_token_id / no_token_id — drop-in replacement for REST behavior.
     - Failure handling: log warning, start REST polling, fire a supervisor task
      that retries WS every 20s (logging each attempt). On WS success, stop REST
      and resume WS. Symmetric on WS disconnect.

     Architecture

     stream_orderbook() becomes a thin consumer over an internal asyncio.Queue.
     Two producer tasks (_ws_producer, _rest_producer) push (market_id, 
     OrderBook) tuples into the queue; a supervisor (_orderbook_supervisor)
     decides which producer is active at any moment. From DataFeed's perspective
      nothing changes — it still async fors over client.stream_orderbook(...).

                      ┌─ _ws_producer (when WS healthy)
     _orderbook_queue ┤
                      └─ _rest_producer (fallback)
            │
            ▼
     stream_orderbook() ── yields ──► DataFeed._stream_orderbooks

⏺ #1 — Cap the WS subscription to top-N markets

  The story behind the empirical failure

  We saw Polymarket cut us off after 20–50 seconds, every time, with no warning
  ("no close frame received or sent" = the server just dropped the connection).
  That's not a network blip — that's a deliberate boot.

  Our subscribe message asked for 9,820 tokens in one connection. To understand
  why that matters, picture what the server sees on its end. For every one of
  those tokens, Polymarket has to:

  1. Watch for any change in that token's order book.
  2. The moment something changes, push a JSON message to us describing it.
  3. Repeat for the next change. And the next. And the next.

  In active hours, prediction markets get hundreds of order updates per second
  across the platform. Our subscription told the server "send us all of them, on
   every token, all the time." From their perspective we look less like a trader
   and more like a denial-of-service. Even if their cap isn't hard-coded, they
  almost certainly have rate-limiting that kicks in once a client's outbound
  message rate crosses some threshold — and we sailed across it on the first
  message.

  Real users of Polymarket's WebSocket — pro traders, arbitrage bots, dashboards
   — typically subscribe to tens to a few hundred tokens, focused on markets
  they actively care about. Nobody streams the entire universe in real-time. The
   reason isn't ideological, it's mechanical: most markets don't move enough to
  justify real-time streaming, and the server providers don't want to pay to
  push you data you don't actually need.

  Why "top-N by volume" specifically

  Volume is the cleanest proxy for "where the action is." A market with $5M
  traded in the last 24 hours is moving constantly — order books shift every few
   seconds, spreads tighten and widen, traders react to news. That's exactly
  where a millisecond-latency WS feed pays off: arb opportunities appear and
  disappear in seconds, and being fresher than the polling competition is how
  you win them.

  A market with $200 traded in 24 hours might tick once an hour. Streaming it in
   real-time wastes bandwidth on both ends. REST polling every two minutes will
  catch literally every meaningful change.

  So the natural split is:
  - High-volume markets (the top 200–500) → WebSocket. This is where arb edges
  live. Sub-second freshness.
  - Everything else (4,500+ markets) → REST sweep, every few minutes. Cheap,
  complete, fine for slow markets.

  Coverage stays at 100%. Latency improves where it matters and stays acceptable
   where it doesn't.

  Why this fixes the connection-dropping problem

  If Polymarket's killing us because we're consuming too many of their server
  resources, the fix is to ask for less. 500 tokens generates roughly 5% of the 
  outbound message rate of 9,820 tokens. That should land comfortably under
  whatever invisible threshold is tripping their disconnect logic, and the WS
  should stay up for hours/days instead of 30 seconds.

  The plumbing is already there — our supervisor and queue don't care how many
  tokens are subscribed; they just route whatever comes in. The change is
  essentially: take the cached market list, sort by volume, slice the top 500,
  hand those to the WS subscribe path.

  Why a config flag instead of hardcoding

  Markets change. During NFL season the top 500 might all be sports markets.
  During an election cycle it shifts to politics. The right cap also depends on
  what Polymarket allows on a given day — they could quietly raise or lower
  their threshold. Putting ws_max_markets in config lets you tune it without a
  code change. Default of 500 is a safe starting point; if WS stays stable for
  hours, push it to 1000; if it still drops, back off to 200.

  #2 — Fix the gather-noise warning

  What's actually happening in the code

  In _orderbook_supervisor, when WS connects we need to run two things at the
  same time: the receive loop (reads messages off the wire) and the heartbeat
  (sends a PING every 10s so the server doesn't think we're dead). I wrote it
  like this:

  recv = asyncio.create_task(self._ws_recv_loop(connection))
  hb = asyncio.create_task(self._ws_heartbeat_loop(connection))
  self._ws_task = asyncio.gather(recv, hb)   # <-- the offender
  done, pending = await asyncio.wait({recv, hb},
  return_when=asyncio.FIRST_EXCEPTION)

  There are two ways to wait for multiple tasks: asyncio.gather() (returns a
  single wrapper) and asyncio.wait() (returns sets of done/pending tasks). I
  accidentally used both. The gather() line creates a wrapper Future that nobody
   actually awaits — await asyncio.wait(...) is what we actually wait on.

  Why Python complains

  When recv crashes with ConnectionClosedError, that exception is stored on the
  task. The asyncio.wait path retrieves it cleanly — we loop over done and
  re-raise it. Fine.

  But the gather() wrapper also observes that same exception. Internally it
  stores the exception in case someone awaits the wrapper. Nobody ever does. So
  when Python's garbage collector eventually cleans up the wrapper, it notices
  "this object had an exception that nobody ever looked at" and prints a warning
   with a full traceback. From Python's perspective, an unobserved exception is
  suspicious — could be a real bug — so it tells you.

  In our case it's a false alarm. The exception IS handled, just through a
  different path. The gather wrapper is a redundant duplicate observer of the
  same event.

  Why the noise actually matters

  Logs are a tool for operators. When something goes wrong in production at 3
  AM, you grep for ERROR or WARNING and you want every hit to be real. Right
  now, every WS reconnect cycle drops a 20-line Python traceback that looks
  identical to a serious crash. After running overnight you might have hundreds
  of these. A human scanning the log to find the actual problem has to mentally
  filter every single one as "ignore, that's just the gather noise."

  This is the kind of small-tax-on-every-debug-session that compounds. Quiet
  logs make real signal stand out.

  The fix is one-line trivial

  Don't create the gather wrapper. Track recv and hb individually (which we
  already do — they're variables right there). The supervisor's existing
  asyncio.wait handles everything correctly. disconnect() already cancels each
  task by name, so we don't need the gather wrapper as a "cancel-both-at-once"
  handle either. Just delete the self._ws_task = asyncio.gather(...) line.

  2. Serialize a JSON message for every single change. This is real CPU work.
  3. Push it over our specific TCP connection. Real bandwidth out of their pipe,
   to our one IP.
  4. Buffer messages we don't read fast enough. Real memory on their box.

  In active hours, Polymarket processes hundreds of order book updates per
  second across the platform. By subscribing to essentially everything, we asked
   them to fan all of that traffic out to our one connection.

  Most servers in this situation defend themselves with what's called a
  token-bucket rate limiter: every connection gets a budget — say, 5 MB of
  outbound or 10,000 messages per minute. As long as you stay under it, you live
   forever. The moment you exceed it, you get killed without a goodbye. The
  "without a goodbye" part is by design — close handshakes are an honorable
  thing servers do for clients, not for clients they're banning.

  That explains everything we saw:
  - Variance in lifetime: depends on how much actual order activity hit our
  subscribed tokens during the session. A quiet 30 seconds keeps us under
  budget; a noisy 30 seconds blows it.
  - Hard TCP close: characteristic of rate-limit-style enforcement.
  - Consistent re-subscription works fine for ~30s: we weren't blacklisted, the
  server just doesn't want to ship us a firehose forever.

  What I haven't proven and how we'd prove it

  To be fully honest, I haven't ruled out these alternatives:

  1. A bug in our recv loop: if we read messages too slowly, the server's send
  buffer to us fills up, and many WS servers kill clients with stuck buffers.
  Our _handle_ws_payload does dict lookups + list manipulation per message —
  synchronous, fast, but not free. Diagnostic: log messages-per-second; if it's
  tiny (<100/s) we're probably fine, if it climbs to thousands and then drops
  dead, we have a backpressure problem.
  2. Polymarket has a 30-second hard cap on all market-channel connections 
  regardless of load: extremely unlikely (no one runs a real-time data feed like
   that), but technically possible. Diagnostic: subscribe to just 5 tokens and
  see if it stays up for hours.
  3. A load balancer between us and Polymarket recycles connections 
  periodically: would be a fixed-interval timer, not variable. Our variance
  argues against this.
  4. The initial book snapshot for 9,820 tokens overwhelmed something: when you
  subscribe, the server sends one book snapshot per token as a starter. That's a
   9,820-message burst in our first second. Either their write side or our
  max_size=8MB could have struggled. Diagnostic: same as #1 above.

  The single experiment that would resolve almost all of this:

  ▎ Subscribe to 50 high-volume tokens instead of 9,820. If WS stays up for 
  ▎ hours, my theory is right and the fix is the subscription cap. If it still 
  ▎ drops in 30 seconds, the problem is somewhere else and we need to look 
  ▎ harder.

  That's actually the same experiment as "implement #1." Capping the
  subscription is both the diagnostic and the fix at once.

  Why I'm comfortable proceeding without proving it first

  The proposed fix is good independent of the diagnosis:
  - If oversubscription is the cause, the cap fixes it.
  - If it's not, we still benefit — focusing WS bandwidth on high-volume markets
   is the right architecture regardless. We'd just learn the real cause from
  logs once the symptom space is smaller and easier to read.

  The alternative — instrumenting heavily, running long experiments, contacting
  Polymarket support — is a lot of effort to confirm something we'd want to do
  anyway. Sometimes the cheapest "diagnostic" is just to implement the most
  likely fix and see what happens.

  The one-paragraph version

  The bot bootstraps once from Gamma to get the market universe (~5,000 markets,
   both their token IDs each). Then a supervisor inside PolymarketClient opens a
   WebSocket to Polymarket's CLOB and subscribes to every token. As long as the
  WS stays alive, real-time book snapshots and price-change deltas pour in and
  get applied to an internal cache — every applied event publishes a fresh
  OrderBook snapshot to a queue. The DataFeed reads from that queue and pushes
  each update through the arb engine. If the WS dies (today: every 20-50s
  because we asked for too much), the supervisor instantly starts a REST polling
   task that rotates through all markets calling GET /book for each, pushing the
   same (market_id, OrderBook) tuples to the same queue — so downstream code
  doesn't even notice the source switched. Every 20 seconds the supervisor tries
   WS again; when it comes back, REST is canceled and we're back on the
  real-time path. Positions refresh independently via REST every 5 seconds.

⏺ When you say "by market," that flips the architecture from a flat universe to

  1. Per-market data we need to capture (parser additions)

  Today's Market dataclass is a snapshot of static facts at fetch time.
  Per-market filtering and routing need more:

  - end_date — currently silently dropped by _parse_market. Needed for
  time-horizon filtering and "winding down before resolution" logic.
  - tags — the array of tag IDs the market belongs to. Today the parser captures
   a string category field that's almost always empty. Real tags live in the
  nested events[].tags[] structure.
  - event_id — which event group this market belongs to (e.g., "2026 NFL
  Champion" event contains 32 markets, one per team). Needed for related-market
  awareness.
  - accepting_orders flag — Gamma exposes it; we don't capture it. A market can
  be active && !closed but not accepting orders during a paused window.
  - order_min_size, order_price_min_tick_size — already on the API response.
  Needed before we can place an order on a market.
  - Volume snapshots over time — Gamma gives volume24hr, volume1wk, volume1mo,
  volume1yr. Capturing just 24h is one data point; the trend tells you whether a
   market is heating up or dying.

  2. Per-market state we need to track at runtime

  Currently the cache holds one struct per market and forgets the rest.
  Per-market thinking needs ongoing state:

  - status: enum — watching, active_opportunity, position_open, cooling_off,
  degraded, resolving_soon, delisted. Drives behavior.
  - first_seen_at / last_book_update_at: when did we add this market, when did
  its book last move? "Stale" markets should fall out of WS subscription.
  - current_spread_yes, current_spread_no: derived from latest book. Tight =
  healthy, wide = drying up.
  - opportunities_seen_count, opportunities_traded_count, realized_pnl:
  per-market scoreboard. Tells you which markets are actually arb-friendly.
  - failure_streak: if we keep getting bad fills or stale prices on this market,
   escalate to auto-blacklist.

  3. Per-market decisions we make

  A flat universe makes one big policy. Per-market lets policy adapt to the
  market's characteristics:

  - Subscription routing: top 200 by volume → WS, rest 50 → REST sweep,
  ultra-low-vol → don't even cache.
  - Position size cap that scales with liquidity: max_position = min(static_cap,
   5% * market_liquidity). A $100K-depth market can absorb a bigger trade than a
   $5K one.
  - Strategy assignment: bundle-arb makes sense everywhere; MM only makes sense
  where spread is wide enough; cross-platform arb only on markets matched to a
  Kalshi twin.
  - Frequency of re-check: hot market with frequent updates gets re-analyzed on
  every tick; sleepy market every 30 seconds is fine.
  - Per-market kill switch: independent of the global one. If market X has eaten
   three losses, freeze it without freezing the rest.

  Bootstrap-only filtering is fragile. Per-market means the filter needs to keep
   voting:

  - Periodic refresh — re-fetch each market from Gamma every N minutes to catch

  - Event-triggered re-check — when book goes flat for >5 min, when 24h volume

  - Add/remove from WS subscription — Polymarket's WS supports
  subscribe/unsubscribe on a live connection. Currently we only subscribe once
  at boot. Need add/remove logic for dynamic universe.
  - Resolution handling — when a market resolves (closed=true or resolved=true),
   unsubscribe, close any positions, freeze the record but keep history.

  "should I lower min_volume?"
  - Per-market log streams: every signal/order/fill tagged with market_id so you
   can grep one market's full history.
  - Per-market "freshness" indicator: how long since the last book update.
  Reveals when a market silently goes dark.

❯ what does the "bot" do?                                                       

⏺ Here's the actual job, in plain English.

  The premise: prediction markets occasionally misprice things

  A prediction market like Polymarket sells you a piece of paper that pays $1 if
   some event happens. Each event has two of these papers: a YES (pays $1 if it
  happens) and a NO (pays $1 if it doesn't). One of them is guaranteed to be
  worth $1 at resolution.

  So if you can buy both YES and NO for less than $1 total, you've locked in
  free money. You don't care which way the event goes — you collect $1 either
  way, and you paid less than $1 for it.

  That's the whole game. Most of the time the math doesn't work out (YES costs
  60¢, NO costs 41¢, total $1.01 — no edge, plus fees). But every now and then,
  for a few seconds, somebody's order book is mispriced and you can buy YES at
  47¢ and NO at 51¢ — total 98¢ — pocketing 2¢ guaranteed. Multiply that by
  hundreds of dollars in size, do it many times a day, and it's a real business.

  What the bot actually does, end to end

  It watches. It streams prices for thousands of Polymarket markets
  continuously, plus it pulls Kalshi (the other big prediction market) for
  comparison. We just spent a few hours on this part — it's the data feed.

  It checks every price update for two kinds of free money.

  1. Bundle arb (inside Polymarket): does YES + NO add up to less than $1 after
  fees? If yes, buy both.
  2. Cross-platform arb (Polymarket vs Kalshi): is the same event cheaper on one
   platform and more expensive on the other? If yes, buy where it's cheap, sell
  where it's expensive.

  It also does market-making on the side. Separate from arb: if a market has a
  wide bid-ask spread (people willing to buy at 40¢, people willing to sell at
  50¢, nobody in between), the bot posts orders in the gap (bid 44¢, ask 46¢)
  hoping to get filled on both sides and pocket the spread. This is a different
  strategy — slower, smaller per trade, but it adds up.

  When it sees something, it doesn't just slam orders. Every potential trade
  gets sanity-checked by a risk manager that asks:

  - Is this market on our blacklist?
  - Would this trade push us over our per-market position cap ($200 default)?
  - Would it push us over our total exposure cap ($5,000 default)?
  - Are we already down more than our daily loss limit ($500 default)?
  - Is the kill switch on?

  Only if all those pass does the order actually get sent to Polymarket.

  It tracks everything. Every position, every fill, every dollar of PnL. A
  portfolio ledger keeps running totals so the risk manager always knows where
  it stands.

  It can run two ways. In dry-run (what you've been doing), it does all the same
   watching, detecting, and "ordering" — but the orders are fake. A simulator
  randomly decides which fake orders would have filled. You see what the bot
  would have done with real money, without risking any. In live mode, the orders
   go to Polymarket for real.

  A typical day in the life of an opportunity

  1. 9:47:03 AM — WebSocket pushes a price_change for some NBA market. YES bid
  drops from 0.52 to 0.48.
  2. 9:47:03 AM — Arb engine recomputes: YES ask is now 0.49, NO ask is 0.49.
  Total = $0.98. After fees, net edge ~1.2¢. Above the 1% min-edge threshold.
  3. 9:47:03 AM — Arb engine emits an "Opportunity" signal. The execution engine
   receives it, checks risk, decides the suggested size is $50.
  4. 9:47:04 AM — Two orders go out: BUY 100 shares of YES at 0.49 ($49), BUY
  100 shares of NO at 0.49 ($49). Total $98 risked.
  5. 9:47:05 AM — Both orders fill. We now own 100 YES and 100 NO.
  6. Whenever the market resolves (could be hours or weeks later) — whichever
  side wins pays out $100. We collected $100, spent $98, made $2.

  That sequence happens (or rather, could happen — most of the time the price
  gap closes faster than we can fill) many times a day across many markets.

  What it explicitly is not doing

  A few things worth knowing about what's NOT happening:

  - Cross-platform arb is detection-only right now. It logs the opportunity and
  shows it on the dashboard, but it doesn't actually place trades on Kalshi —
  the Kalshi client is read-only. Trading on Kalshi requires its own auth/order
  code that hasn't been written yet.
  - No directional betting. The bot has no opinion on whether the Lakers will
  win or who'll be the next president. It's only looking for moments when YES +
  NO are mispriced relative to each other, or when two markets disagree. Pure
  arbitrage — neutral on outcome.
  - No automated risk decisions beyond the caps. It won't decide to "go bigger
  because we're hot" or "pull back because something feels off." The rules are
  static.
  - No human-in-the-loop on individual trades. Once it's running, it just runs.
  If you want to stop it, you trip the kill switch in config or kill the
  process.

  The web dashboard is just a window into all of this

  The FastAPI server we've been poking at on port 8888 is just a viewer. It
  doesn't do anything — it reads the bot's internal state and renders it as HTML
   and JSON endpoints. Open the page in a browser, you see what the bot is
  seeing in real time: which markets are loaded, what opportunities have been
  spotted, what trades have happened, what your PnL is.

  The bot would work without the dashboard. The dashboard exists so you can
  watch what it's doing without staring at log files.

  ---
  That's the whole bot. A patient, neutral watcher that hunts for pricing 
  mistakes on prediction markets, sanity-checks itself before acting, and tracks
   the score.

⏺ Good catch — this is actually the right question to ask, and the answer
  reveals something important about what you're actually seeing in those logs.

  Three data paths, not one

  Polymarket has two: WebSocket (fast, when it's up) and REST polling (slow,
  always). Kalshi has one: REST polling only. The cross-platform engine doesn't
  know or care which of these filled the cache — it just reads whatever's there.

  ┌──────────────────────────┐
  │ Polymarket WebSocket     │ ─┐   when alive: pushes fresh books
  └──────────────────────────┘  │
                                ├──► shared Polymarket book cache
  ┌──────────────────────────┐  │
  │ Polymarket REST polling  │ ─┘   always running (when WS dies): fills the
  cache slower
  └──────────────────────────┘

  ┌──────────────────────────┐
  │ Kalshi REST polling      │ ────► shared Kalshi book cache
  └──────────────────────────┘       always running, ~2s per batch of 100
  tickers

  The cross-platform arb engine sits downstream of both caches. Its trigger is
  Kalshi, not Polymarket: every time a Kalshi book updates (every couple
  seconds), it looks up the corresponding Polymarket book in the cache and
  compares.

  So during our test run, when WS was down for 20s at a time, the Polymarket
  cache was being refreshed by the REST fallback — slower, but still flowing.
  The arb engine got new Kalshi prices every 2 seconds, and for each one it
  asked the cache "what's Polymarket showing for this market right now?" The
  cache answered with whatever it last had — which might have been 30 seconds
  old, or 2 minutes old, depending on when REST last hit that particular market.

  The uncomfortable implication

  Those "CROSS-PLATFORM OPP" log lines you saw scrolling by were real in the
  sense that the cache said so. But the freshness of the Polymarket half varied
  wildly depending on whether WS was up.

  When WS was alive: that side of the comparison was milliseconds-old. Real
  signal.

  When WS was dead and we were on REST fallback: that side was up to a few
  minutes old. Some of those "opportunities" might have been ghosts —
  Polymarket's price had probably already moved by the time we saw the gap, and
  if we'd tried to trade, the edge would have evaporated.

  This is exactly why we never lost any data despite the WS being unstable — but
   it's also why "no data loss" isn't quite the same as "fresh data." We had
  stale data filling the gaps, and stale arb signals look identical to real ones
   until you actually try to fill them.

  Why this doesn't matter right now

  Two reasons it hasn't bitten us:

  1. We're in dry-run mode — no real orders. Even a ghost opportunity costs
  nothing.
  2. Cross-platform is detection-only anyway — the Kalshi client is read-only,
  so even if we wanted to act on a cross-platform signal, we couldn't.
  Polymarket has trading code, Kalshi doesn't.

  So during this session, the system has been doing exactly what it was designed
   to do: watch and log. The freshness problem only becomes a real risk if/when
  we go live with actual cross-platform trading, which would also require
  building out the Kalshi trading client.

  And it explains the empty /api/opportunities endpoint

  Remember when we hit /api/opportunities and it returned []? That endpoint is
  for single-platform bundle arb on Polymarket — and bundle arb requires
  real-time YES + NO prices to be co-fresh. During WS-down periods, YES might be
   2 minutes old and NO might be 30 seconds old (because REST refreshed them at
  different times in its rotation). That makes any bundle math meaningless, so
  the engine smartly produces nothing. Cross-platform was finding signals
  because it's looking at a different pair (Polymarket-vs-Kalshi) and is more
  tolerant of one-sided staleness.

  In one sentence

  The bot has been "working" the whole time because the REST fallback kept the 
  cache populated — but the cross-platform signals you saw were a mix of 
  real-fresh-WS-backed ones and stale-REST-backed ones, and there's no current 
  way to tell them apart in the log.

  Want me to think about how we'd add a freshness tag to each signal, so you can
   filter "only show me opportunities backed by < 5-second-old Polymarket data"?
